# 테스트 — 느림과 흔들림의 원인

> 테스트가 느려지거나 가끔 실패할 때 실제로 찾은 원인. 새 시험을 쓸 때의 규칙은
> `tests/gui/AGENTS.md`에 있다.
> 색인: [`../design-decisions.md`](../design-decisions.md).

## 전체 시험 742초 → 443초 (2026-09-30)

유지보수 점검에서 가장 느린 시험 둘(테마 적용 22~36초, 동기화 병합 11~18초)과 가끔 실패하는
시험 하나를 조사했다. 둘은 앱이 아니라 **시험 환경**이 원인이었고, 하나는 앱 코드도 고칠
거리를 드러냈다.

### 테마 시험이 느린 이유는 앞선 시험들이 남긴 위젯이었다

테마 시험이 돌 때 앞선 GUI 시험들이 남긴 위젯이 **9,701개**(최상위 164개, 모두 숨김) 살아
있었다. 전역 QSS를 바꾸면 Qt가 살아 있는 모든 위젯을 다시 polish하므로 `setStyleSheet` 한
번에 약 11초가 걸렸다. 테마 코드 자체는 멀쩡했다.

누수 경로는 둘이었다(시험마다 위젯 수 증가를 재는 프로브로 찾았다).

- **삭제 예약만 되고 집행되지 않았다.** 시험에는 앱처럼 도는 이벤트 루프가 없어서
  `deleteLater()`(qtbot의 정리 포함)가 세션 끝까지 실행되지 않는다. `tests/gui/conftest.py`의
  autouse 픽스처가 시험마다 `sendPostedEvents(None, DeferredDelete)`를 부른다 — 앱에서는
  이벤트 루프가 하는 일이다.
- **qtbot에 등록되지 않은 위젯이 순환 참조로 남았다.** 전 세대 GC가 거의 돌지 않아 회수되지
  않는다. 주범 시험 5개에 `qtbot.addWidget`을 넣었다.

결과: 테마 시험 시점의 위젯 9,701 → 0, `setStyleSheet` 11초 → 0.2ms.

### 동기화 병합 시험은 DB 초기화 25번이었다 — 앱 코드도 빨라졌다

cProfile로 보니 시간의 95%가 `Database.initialize()`였다(새 DB 약 0.9초 × 25). 초기화마다
연결을 약 55번 열고 닫으며 쓰기 커밋마다 fsync를 치른다.

앱 코드(`infrastructure/persistence/database.py`)를 고쳤다 — 결과 스키마는 같다.

- 스키마 스크립트를 한 트랜잭션으로 묶었다(CREATE 약 50개가 하나씩 커밋되던 것).
- 적용된 마이그레이션 id를 한 번에 읽고 적용된 것은 건너뛴다(마이그레이션마다 연결을 열어
  확인하던 것).

그래서 **이미 초기화된 DB의 initialize — 두 번째 실행부터의 앱 시작 경로 — 가 70ms → 5ms**가
됐다. 새 DB 초기화(약 0.9초)는 그대로다. 남은 비용은 마이그레이션 쓰기 커밋의 fsync인데,
줄이려면 `synchronous` 설정을 바꿔야 해서 **내구성이 달라지므로 손대지 않았다.** 초기화 동안
연결 하나를 열어 두는 방법도 시도했지만 오히려 느려져(5ms → 13ms) 되돌렸다.

시험은 한 번 초기화한 템플릿 DB 파일을 복사한 뒤 `initialize()`를 다시 부른다 — 시작 경로는
그대로 밟는다. 17.8초 → 1.45초. (`test_sync_entities` 등 새 DB를 여러 번 만드는 시험에 같은
방식을 공용 픽스처로 넓히면 더 줄일 수 있다.)

### 괄호 키 시험은 창 활성화를 기다리지 않았다

픽스처가 창 노출(`qWaitForWindowExposed`)만 기다리고 활성화는 기다리지 않았다. 활성화는
비동기로 늦게 오고, `QApplication.focusWidget()`은 **활성 창의** 포커스 위젯만 돌려주므로
부하 중에는 None이 된다. 재현 스크립트로 확인하니 창 안의 포커스 소유자는 맞았다 — 포커스
위임 배선은 정상이고 OS 활성화 타이밍만 문제였다. 활성화를 `waitUntil`로 기다리고, 판정은
활성 여부와 무관한 `window().focusWidget()`으로 바꿨다.

### 남은 관찰

누수를 없앤 뒤에도 `ThemeManager.theme_changed`의 수신자가 약 2,200개 남는다. `gui/`의
연결은 모두 바운드 메서드라 시험 쪽에서 연결한 콜러블로 보인다. emit 비용은 무시할 수준이라
그대로 뒀다.
