# 다운로드·자동 업데이트

> 다운로드 실패 처리, 대기 표시, 자동 업데이트 흐름.
> 색인: [`../design-decisions.md`](../design-decisions.md).

## 항목별 기록

- **자동 업데이트(백그라운드 다운로드 + 종료 시 설치)** — ⚠ **이 항목은 v1.29.0까지의 동작이다.** v1.30.0에서 ① 발견 즉시 받던 것을 **배지를 눌러야 받도록** 바꿨고(진행률 연출이 보이게), ② 설치가 **PID 소멸을 기다렸다가** 돌고 끝나면 앱을 자동 재기동하며, ③ 발견만으로는 1시간 인터벌을 소진하지 않는다. 지금 동작은 아래 "자동 업데이트 UI — 배지·진행률·무중단에 가까운 설치 (v1.30.0)" 항목을 봐야 한다. 아래는 그때의 기록이다. — 레이어는 `domain/shared/ports.py:IUpdateChecker`(+`UpdateInfo` 값객체) ← `application/updater/` ← `infrastructure/updater/` ← `gui/updater/`로 다른 기능과 동일한 규약을 따른다(GUI가 GitHub API를 직접 부르지 않는다). 시작 시 조용히 확인(`UpdateController.check_silently`, `AUTO_UPDATE_CHECK`+1시간 간격)해 새 버전이 있으면 **사용자 조작 없이 백그라운드로 다운로드**(`UpdateDownloadWorker`)한다. 완료되면 `gui/updater/pending.py:write_pending_update`가 `<tempdir>/ovc_pending_update.txt`(2줄: 인스톨러·exe) 마커를 기록하고(**앱 종료는 안 함**) `update_ready` 시그널을 방출 → `MainWindow`가 **설정 기어 버튼에 빨간 점 배지(`_NavButton.set_badge`)+"업데이트 준비 완료" 툴팁**을 표시하고 설정 헤더에 '지금 설치' 버튼을 노출한다. 실제 설치는 **앱을 닫을 때** `main.py` 종료 tail이 마커를 읽어 조용히 설치 후 재실행(설치는 실행 중 불가하므로). '지금 설치'는 `install_now`가 앱을 종료(마커가 이미 있으므로)해 즉시 설치를 유도한다. 마커 기록은 `UpdateDialog`(수동 경로)와 공유한다. **다운로드는 130MB가 넘어 API 조회용 타임아웃(10초)으로는 끊긴다** — 실제로 `Read timed out`으로 여러 번 실패했다. `download_asset`은 `_DL_TIMEOUT=(10,60)`을 쓰고, 끊기면 `Range`로 이어받아 `_DL_MAX_ATTEMPTS`(4)회까지 재시도한다(백오프 3초×시도). 이어받기 때문에 sha256은 스트리밍 중 누적하지 않고 완료된 `.part` 파일에서 한 번에 계산한다(`_sha256_of`). 본문이 content-length보다 짧게 끝나도 실패로 보고 재시도한다. **인터벌(1시간)은 성공했을 때만 소진한다**(`_mark_checked` — none_found·다운로드 완료·스누즈). 예전엔 확인을 시작하자마자 기록해, 다운로드가 실패하면 다음 1시간 동안 재확인이 막히고 앱을 다시 켜도 배지조차 안 떠 업데이트할 방법이 없었다. **다운로드 실패 시에도 설정 헤더에 설치 버튼을 노출한다** — `update_notification` → `MainWindow._on_update_notification` → `SettingsPanel.set_update_available(dto)`(상태 '업데이트 있음', 버튼 '설치하기' → `install_now`가 마커 없으면 `UpdateDialog` 수동 다운로드로 폴백). 예전엔 배지만 켜져 설정 화면에서 할 수 있는 게 없었다. 헤더의 **'확인' 버튼**(`check_update_requested`)으로 인터벌과 무관하게 즉시 재확인할 수 있다 — 이 시그널은 예전엔 선언만 되고 방출하는 곳이 없는 죽은 코드였다. 확인 중에는 `check_started`/`check_finished` → `set_update_busy`로 버튼을 잠근다.
- **다운로드 403 Forbidden + 조각난 `.part` 파일 (해결)** — 위 스트리밍 재생과 **원인은
  같지만 경로는 달랐다**: `YtDlpAdapter.download()`(`infrastructure/downloader/ytdlp_adapter.py`)는
  스트리밍 경로(`_StreamWorker`)의 클라이언트 폴백이 생기기 전에 작성됐고 그 뒤로도
  이식되지 않아, 기본(web) 클라이언트의 간헐적 403을 그대로 맞았다. yt-dlp가
  포맷(영상/오디오)별로 조각을 받다가 403으로 중단되면 `<제목>.f<itag>.<ext>.part`
  임시 파일이 병합·정리되지 않고 디스크에 남는다(실사용 데이터에서 재현: `f137.mp4.part`·
  `f399.mp4.part`). 대응: `download()`도 `_DOWNLOAD_CLIENTS`(기본→android→ios→tv, 스트리밍과
  동일한 순서)를 돌며 403일 때만 다음 클라이언트로 재시도하고(403이 아닌 오류는 클라이언트를
  바꿔도 소용없으므로 즉시 전파), 마지막 클라이언트도 실패하면 그대로 예외를 전파한다.
  **`.part` 정리는 성공 시에도 필요하다** — 첫 클라이언트가 403으로 조각을 남기고 두
  번째 클라이언트가 성공하는 흔한 경우, 정리를 "완전 실패했을 때만" 돌리면 그 조각은
  영원히 남는다. `_progress_hook`이 매 조각의 `tmpfilename`을 `_tmp_files_seen`에
  기록해 두고, 성공·완전실패 양쪽 경로 끝에서 `_cleanup_partial_files()`가 그 목록을
  지운다(이미 정상 병합·삭제된 파일은 `missing_ok=True`라 안전). 회귀 테스트:
  `tests/unit/infrastructure/test_ytdlp_download_retry.py`.

## 게이트에 걸린 다운로드는 '대기 중'이라고 말한다 (v1.27.1)

예약 시간대·동시 한도에 걸린 작업은 진행률이 영원히 0이다. 카드에 '0%'로 그리면
멈춘 것처럼 보이고, 왜 안 받는지 알 길이 없다(CLAUDE.md — 상태를 말하지 않는 화면을
만들지 않는다). 그래서 카드에 '대기 중'을 띄우고, 목록 위에 **이유**를 한 줄 적는다
("예약 시간대(23시~7시)를 기다립니다 — 3건 대기").

그리고 **다운로드를 멈출 길이 아예 없었다** — `cancel_download()`는 있었지만 화면에서
부르는 곳이 없어, 잘못 넣은 주소나 몇 시간짜리 녹화를 되돌리려면 앱을 끄는 수밖에
없었다. 카드 우클릭에 붙였다(끝난 카드에는 띄우지 않는다 — 눌러도 아무 일이 없다).

회귀 테스트: `tests/gui/test_download_waiting_ui.py`.

## 자동 업데이트 UI — 배지·진행률·무중단에 가까운 설치 (v1.30.0)

### 왜 손댔나

업데이트가 **사용자에게 거의 보이지 않았다.** 새 버전을 찾으면 앱이 조용히 179MB를
받고, 알림은 좌하단 기어의 빨간 점 하나였다. 그 점의 뜻을 알려면 설정 화면까지
들어가야 했고, 설치는 "앱을 닫으면 자동으로" 이뤄졌다 — 사용자가 직접 앱을 닫기
전까지는 영원히 일어나지 않는다.

### "앱이 켜진 채로 설치"는 불가능하다

실행 중인 `.exe`와 `_internal/*.dll`은 Windows가 잠근다. 파일 교체 순간에는 앱이
반드시 내려가 있어야 한다. 그래서 목표를 **공백 최소화**로 바꿨다: 다운로드는 앱이
켜진 채 끝내고, 배치가 **우리 PID가 사라지는 것을 감시하다가** 죽는 즉시 설치를
시작하며, `/SILENT`로 인스톨러 진행 막대를 띄워 공백 동안에도 화면에 무언가를 남긴다.

### 이 작업에서 드러난 기존 버그 셋

세 가지 모두 **조용히 실패해서 아무도 몰랐던** 것이다.

1. **`timeout /t 5`가 한 번도 기다린 적이 없다.** 배치를 `DETACHED_PROCESS`로 띄우면
   콘솔이 없고, 콘솔이 필요한 명령은 즉시 실패한다. "5초 대기"라고 적혀 있었을 뿐
   실제로는 0초였고, 파일 잠금을 막아 준 것은 인스톨러의 `CloseApplications=force`
   뿐이었다. `CREATE_NO_WINDOW`로 바꿔 창은 숨기되 콘솔은 준다.
2. **`find`가 GNU find로 잡힌다.** Git for Windows가 깔린 PC에서는 그쪽
   `usr/bin/find.exe`가 PATH 앞에 있고, 인자를 파일 경로로 해석해 실패한다. 그러면
   `|| goto ready`가 발동해 **PID 대기가 통째로 사라진다.** 시스템 도구는 절대 경로로
   부르고, 이름이 겹치지 않는 `findstr`을 쓴다.
3. **배치 파일 인코딩.** 사용자 이름이 한글이면 임시 경로에 한글이 섞이는데(한국어
   사용자에게 흔하다) ascii로 기록하면 실패해 업데이트가 통째로 막힌다. 시스템 ANSI
   코드페이지로 기록하되, **우리가 적는 명령어는 ASCII만** 쓴다 — 반대로 배치에 한글
   주석을 넣으면 영문 Windows에서 기록이 실패한다.

### 발견은 인터벌을 소진하지 않는다

다운로드를 "발견 즉시"에서 "누를 때"로 옮기면서 `_mark_checked()` 위치가 문제가 됐다.
발견 시점에 1시간 인터벌을 소진하면 **앱을 껐다 켰을 때 확인을 건너뛰어 배지가 뜨지
않고, 사용자는 업데이트할 방법을 잃는다.** 이 저장소가 이미 한 번 밟은 함정이라
(`tests/gui/test_update_flow.py` 상단 회귀 배경) 발견은 종결된 결과로 치지 않는다.
대가로 업데이트가 대기 중이면 1시간마다 재확인하는데, 그 사이 더 새 버전이 나오면
배지가 그쪽으로 갱신되므로 의도된 동작이다.

### 커스텀 타이틀바 — 왜 네이티브 훅인가

OS 제목 표시줄에는 위젯을 넣을 수 없어 frameless로 갔다. 단순히
`Qt.FramelessWindowHint`만 주면 **Aero Snap·창 그림자·8방향 리사이즈·최대화
애니메이션·`Win+화살표`·시스템 메뉴가 전부 사라진다.** 특히 "최대화 상태에서
드래그하면 복원되며 커서를 따라오는" 동작은 DPI가 다른 모니터 사이에서 수식으로
맞추기가 사실상 불가능하다.

그래서 `WS_THICKFRAME | WS_CAPTION`을 **남겨 둔 채** `WM_NCCALCSIZE`로 프레임 영역만
0으로 만든다. 위 동작이 전부 OS 기본으로 들어오고, 우리가 할 일은 `WM_NCHITTEST`에서
"여기는 제목 표시줄"이라고 답해 주는 것뿐이다 — **드래그 코드를 한 줄도 쓰지 않는다.**

이 방식의 대표적 함정 둘을 함께 처리했다. 최대화 시 프레임 두께만큼 되줄이지 않으면
클라이언트가 "작업영역 + 프레임 두께"를 통째로 가져가 사방이 화면 밖으로 나가고
(우측 스크롤바가 잘린다), 자동숨김 작업표시줄이 있는 변을 100% 덮으면 마우스를 대도
표시줄이 다시 나오지 않는다(2px 양보). 실측 결과 최대화 창이 작업영역과 **사방 넘침
0**으로 일치한다.

### `super().nativeEvent()`가 프로세스를 죽인다

PyQt 6.11에서 파이썬 오버라이드가 기본 구현을 호출하면 **액세스 위반으로 앱이 즉시
사라진다**(0xC000041D, 창이 만들어지는 바로 그 순간). 화면에 아무것도 안 나오고 로그도
없어 원인을 찾기 어렵다 — 최소 재현으로 좁혀서야 드러났다. `return False, 0`이 의미가
같고(Qt 기본 구현도 "처리하지 않았다"만 반환한다) 안전하다. 누가 "기본 구현도 불러야
맞지 않나" 하고 되돌리는 것을 `tests/gui/test_frameless_guard.py`가 AST로 막는다.

### Win11 분할 배치(스냅 레이아웃)는 공짜가 아니다

최대화 버튼 위에서 `HTMAXBUTTON`을 돌려주면 Windows 11 이 분할 배치 메뉴를 띄워 준다.
대신 **그 영역의 마우스를 OS 가 가져간다** — Qt 의 `enterEvent`/`leaveEvent`도, 클릭도
더 이상 오지 않는다. 그래서 비클라이언트 마우스 메시지 4종을 직접 받아 호버와 클릭을
버튼에 되돌려 줘야 한다. 이 처리를 빼면 **메뉴는 뜨는데 버튼이 먹통이 되는** 상태가
되고, 화면만 봐서는 원인을 알 수 없다(그래서 v1.30.0에서는 범위 밖으로 미뤄 뒀다).

호버를 켤 때 `TrackMouseEvent(TME_NONCLIENT|TME_LEAVE)`를 함께 걸어야 한다. 안 걸면
`WM_NCMOUSELEAVE`가 오지 않아 **버튼 밖으로 나가도 호버가 켜진 채 남는다.**

누름(`WM_NCLBUTTONDOWN`)은 삼키고 토글은 **뗄 때** 한다. 기본 처리에 맡기면 OS 가 자기
방식으로 버튼을 그리려 하고, 뗄 때 토글하는 편이 "눌렀다가 밖에서 떼면 취소"라는
실제 버튼 동작과도 맞는다.

#### 히트테스트가 맞아도 메뉴는 안 뜰 수 있다 — `WS_POPUP`

`HTMAXBUTTON`을 정확히 돌려주는데도 분할 배치 메뉴가 뜨지 않았다. 메모장과 창 스타일을
나란히 놓고서야 보였다 — 차이가 **딱 한 비트**였다.

    메모장   0x14CF0000
    우리 앱  0x96CF0000   ← WS_POPUP(0x80000000)

Qt가 `FramelessWindowHint` 때문에 창을 팝업으로 만드는데, **셸은 팝업 창을 평범한 앱
창으로 보지 않아 메뉴를 붙이지 않는다.** 히트테스트가 아무리 맞아도 소용없다.
`patched_style()`이 이 비트를 끄고, `TestPatchedStyle`이 다시 켜지는 것을 막는다.

#### `DwmExtendFrameIntoClientArea` 가 분할 가이드를 막는다

`WS_POPUP` 을 끈 뒤에도 가이드가 뜨지 않았다. 창 스타일·확장 스타일·클래스 스타일·
DWM 속성을 메모장과 전부 대조했지만 의미 있는 차이가 없었다.

원인은 **우리가 그림자를 살리려고 넣은 호출**이었다. 프레임을 클라이언트 안으로
확장하면(`DwmExtendFrameIntoClientArea`) 셸이 분할 배치 메뉴를 띄우지 않는다.
`DwmSetWindowAttribute(DWMWA_NCRENDERING_POLICY, ENABLED)` 는 그대로 둬도 되고,
`WS_THICKFRAME | WS_CAPTION` 만으로도 DWM 이 그림자를 그려 준다.

실측(최대화 버튼 아래 영역의 픽셀 변화율, 메모장 0.839 가 기준):

| 시도 | 변화율 | |
|---|---|---|
| 현재(프레임 확장 유지) | 0.003 | 안 뜸 |
| 위쪽 프레임 1px 남기기 | 0.003 | 안 뜸 |
| **프레임 확장 제거** | **0.844** | **뜸** |
| 위쪽만 확장 `(0,0,1,0)` | 0.003 | 안 뜸 |

#### 가이드가 떴는지 **자동으로** 확인하는 법

앞서 "자동 검증이 안 된다"고 적었는데, 방법이 틀렸던 것이다. 창 목록(`EnumWindows`)
비교로는 메모장에서도 못 잡았다 — 가이드가 일반적인 최상위 창으로 잡히지 않는다.

**최대화 버튼 아래 영역을 `BitBlt` 로 찍어 호버 전후를 비교**하면 잡힌다. 창의 종류를
알 필요가 없고, 뜨면 그 영역의 80% 넘는 픽셀이 바뀐다. 커서는 `SendInput` 으로
조금씩 움직이고(순간이동은 셸의 호버 감지를 못 깨운다), 창을 최상위로 올려야 한다
(가려져 있으면 마우스 메시지가 우리에게 오지 않는다).

**대조군을 먼저 통과시키는 것이 핵심이다.** 메모장에서 감지되지 않으면 그 실행은
버리고 방법부터 고쳐야 한다 — 그러지 않으면 "안 뜬다"가 기능 문제인지 감지 문제인지
알 수 없고, 실제로 그 혼동 때문에 한 번 엉뚱한 결론을 냈다.

#### 최대화를 잴 때는 **클라이언트** 사각형을 본다

`WM_NCCALCSIZE`가 정하는 것은 창 사각형이 아니라 **클라이언트 사각형**이다. 창 사각형만
재면 최대화된 창이 작업영역보다 사방으로 커 보이는데, 그것이 정상이다 — Windows 는
`WS_THICKFRAME` 창을 최대화할 때 창 사각형을 "작업영역 + 프레임 두께"로 잡는다.

실측(4K/150% 화면, 작업영역 3840×2088):

| | 창 | 창 넘침 | 클라이언트 | 클라 넘침 |
|---|---|---|---|---|
| 메모장 | 3862×2110 | 11,11,11,11 | 3844×2101 | 2,11,2,2 |
| 우리 앱 | 3862×2110 | 11,11,11,11 | 3840×2088 | **0,0,0,0** |

창 넘침은 메모장과 **같다**. 우리 클라이언트가 0인 것은 프레임을 지우고 그 자리까지
직접 그리기 때문이고, 이것이 의도한 모습이다.

한 번 이걸 혼동해 "`Win+↑`·타이틀바 더블클릭 경로에서만 11px 넘친다"고 오진하고,
`GetWindowPlacement`가 `WM_NCCALCSIZE` 시점에 낡았을 것이라 추정해 판정을 사각형
기반으로 갈아엎었다. 변경 **전** 빌드로 클라이언트를 재 보니 이미 `0,0,0,0`이었다 —
버그가 없었고 가설도 거짓이었다. 그래서 되돌렸다.

교훈: **고치기 전에 고장을 먼저 재라.** 그리고 재는 대상이 맞는지부터 확인하라 —
정상 동작하는 앱(메모장)과 나란히 놓으면 5분이면 갈린다.

#### 이 버그를 늦게 찾은 이유 — 감지 방법이 틀렸다

히트테스트도 맞고 호버·클릭 왕복도 되니 **자동 검증은 전부 초록이었다.** 메뉴만 안 떴다.

메뉴 등장을 자동으로 확인하려 했지만 `SetCursorPos`도 `SendInput`도 셸의 호버 감지를
깨우지 못했다. 대조군으로 메모장을 같은 방법으로 훑었더니 **거기서도 안 떴고**, 그래서
"합성 입력의 한계이지 우리 문제가 아니다"라고 결론 냈다 — 그 결론이 진짜 버그를 덮었다.
대조군이 실패한 이유는 맞았지만, 그것으로 우리 창의 무죄를 증명할 수는 없었다.

교훈: **관찰할 수 없다는 것이 정상이라는 뜻은 아니다.** 검증 수단이 막혔을 때는
'확인 못 함'으로 남겨야지 '문제 없음'으로 바꿔 읽으면 안 된다. 그리고 막혔을 때는
**대상을 정상 동작하는 것과 나란히 비교**하는 쪽이 빠르다 — 스타일 비교 한 번이
합성 입력을 다섯 번 고쳐 보는 것보다 결정적이었다.

메뉴가 실제로 뜨는지는 여전히 사람이 마우스를 올려 봐야 한다. 대신 회귀 테스트는
**창 스타일·히트테스트 값·메시지 왕복** 셋을 지킨다.

### 배지 글자는 두 번 그린다

진행률 채움 경계가 글자 한가운데를 지나가므로 펜 하나로는 어느 쪽이든 묻힌다.
처음에는 "50% 넘으면 글자색을 바꾼다"로 했는데, 대비를 재 보니 **11개 테마 전부에서**
채움 위 `text_primary`가 AA 미달이었다(zinc 2.56:1). 채워진 쪽은 `text_on_accent`,
나머지는 `text_primary`로 각각 자기 영역에 잘라 그린다
(`test_badge_label_on_progress_fill`이 고정).

## 다운로드 화면 성능 — 성능 배치 4

### N+1: 카드마다 상세 조회를 타던 refresh

`DownloadPanel.refresh`가 제목·썸네일을 채우려고 URL마다 `find_title_by_url`/
`find_thumbnail_by_url`을 불렀고, 각각이 `GetVideoIdByUrl` + `GetVideoDetail`(연결 6개,
게다가 상세는 **전체 태그 목록**을 읽었다)을 탔다. 실측: 실데이터(카드 14장) refresh 519ms·
DB 연결 169번, 5k 라이브러리·이력 50행 3,156ms·연결 701번.

- `IVideoRepository.find_briefs_by_urls(urls)`가 URL 묶음을 **연결 1회**로 읽는다(`IN` 청크 400개,
  청크는 한 연결 안에서). 키는 호출자가 넘긴 URL 그대로, 조회는 `normalize_video_url`로 하므로
  `youtu.be` 표기도 단건 조회와 같은 영상을 찾는다.
- `GetVideoBriefsByUrlsHandler` → `LibraryViewModel.find_briefs_by_urls`(제목 대체 판단·썸네일
  `Path.exists`는 여기서, 존재하는 파일만 채운다) → `DownloadPanel(briefs_provider=...)`.
- `GetVideoDetailHandler`는 `tag_names_for(video_id)`(`video_tags JOIN tags`)로 그 영상의
  태그명만 읽는다. DTO 필드 `tags`는 그대로다.
- `RecordingVideoRepository`는 `SqliteVideoRepository`의 하위 클래스라 읽기 메서드가 그대로 통한다.

### 라이브 카드가 멈춰 보이던 결함

`_HistoryModel.update_active_progress`가 `percent`만 비교했다. 라이브 녹화는 총량을 몰라
`percent`가 늘 0이라, 받은 용량·경과 시간이 바뀌어도 `dataChanged`가 나가지 않았다.
이제 카드가 읽는 값(`percent`·`downloaded_bytes`·`total_bytes`·`elapsed_sec`) 중 하나라도
바뀌면 보내고, 전부 같으면 헛 다시 그리기를 하지 않는다.

### 이벤트 유실

`DownloadQueueAggregate.pull_events`는 `list(self._events)` 복사 뒤 `clear()`였다. 그 사이에
다른 워커 스레드의 `_raise`가 끼면 복사본에는 없는데 `clear()`로 지워져 **영원히 유실**됐다
(반대로 두 스레드가 같은 이벤트를 가져가는 중복도 가능했다). `threading.Lock`으로 `_raise`와
`pull_events`를 직렬화하고, 비우는 대신 목록을 **통째로 교체**한다. 잠금은 표준 라이브러리라
도메인 순수성이 유지되고, 구간이 리스트 연산뿐이라 경합 비용이 없다(8스레드×2000 시험이
발행 건수 == 회수 건수를 지킨다).

### 진행률 합치기

yt-dlp 진행 콜백은 초당 수십 번이고 그때마다 `queue_changed` → 화면의 `vm.queue`(DB) +
모델 갱신이 돌았다(동시 5개 다운로드 중 5초에 refresh 14번, 최대 정지 3.5~4.8초).
`DownloadViewModel._on_progress`가 `PROGRESS_MIN_INTERVAL_MS`(150ms) 간격으로 합친다. 간격이
지났으면 즉시, 아니면 '보낼 것이 남음' 표시만 하고 GUI 스레드의 trailing 타이머가 **마지막
상태를 한 번** 보낸다(워커 스레드에서는 `QTimer`를 못 켜므로 큐잉 신호 `_progress_deferred`
를 거친다). 완료·실패·취소는 합치지 않고 즉시 보낸다. 타이머는 `shutdown()`에서 멈춘다.
시계는 모듈 수준 `_now`(= `time.monotonic`)라 시험이 바꿔 끼운다.

### 메모 저장 실패와 `busy_timeout`

`save_notes`가 실패해도 로그만 남아 사용자는 저장됐다고 믿은 채 내용을 잃었다 — 이제
`error_occurred`로도 알린다. `Database.BUSY_TIMEOUT_MS`를 명시하고 연결마다
`PRAGMA busy_timeout`을 건다(쓰기 잠금 경합 때 기다리는 최대 시간이 코드에 드러난다).
