# 재생·스트리밍·자막·음성 인식

> 앱 내 재생(스트리밍·remux·화질), 자막(선택·번역·동시 표시), 음성 인식, 이어보기.
> 색인: [`../design-decisions.md`](../design-decisions.md).

## 항목별 기록

- **지금 재생 중 미니바** — 상세 화면을 떠나도 **재생 중이면** 멈추지 않고 창 하단
  띠(`MiniPlayerBar`)로 넘긴다. 멈춰 있었으면 예전처럼 정지한다 — 안 보이는 곳에서
  소리도 없이 자원만 붙들 이유가 없다. 핵심은 **플레이어를 옮기지 않는다**는 것이다:
  `VideoDetailWidget`은 `_nav_stack`에 살아 있는 위젯이라 화면을 목록(0)으로 바꿔도
  `QMediaPlayer`는 계속 재생한다. 그래서 복귀(`mini_open`)는 **다시 불러오는 게 아니라
  스택 인덱스만 1로 되돌리는 일**이고, 그 덕에 재생이 한 번도 끊기지 않는다(위치·화질·
  자막 상태까지 그대로). 여기에 재로드가 끼면 그 장점이 통째로 사라지므로
  `tests/gui/test_mini_player.py`가 "다시 불러오지 않는다"를 못박는다. 띠는 창 바닥
  (상태바 위)에 두어 다운로드·설정 페이지에서도 보이며, 위치·재생 여부는 신호가 아니라
  **0.5초 타이머로 훑는다**(`positionChanged`는 초당 수십 번 온다). 미니바로 듣는 중의
  자동 다음곡은 `stay_on_list=True`로 **화면을 뺏지 않고** 다음 곡만 갈아 끼우며, 이때
  연관 목록(재생목록)을 그대로 넘겨야 그다음 곡으로도 이어진다(`related=None`으로 열면
  지금 보고 있는 카테고리 목록으로 갈아타 버린다).
- **영상 자막 (언어 선택 · 자동 번역 · 두 줄 동시 표시)** — 영상에 딸린 YouTube 캡션을
  컨트롤바 `CC` 메뉴에서 고른다. **가사 자막(💬)과는 별개 기능**이다(가사는 노래 정보에서
  오고 자막은 그 영상의 캡션이다). 칸이 **둘**이라 원어와 모국어를 동시에 볼 수 있고,
  칸마다 '자동 번역' 대상을 따로 고른다. 렌더는 기존 `LyricsOverlay`를 그대로 쓰되
  `set_subtitle_texts(primary, secondary)`로 **한 번에** 세팅한다(따로 넣으면 짝이 어긋난
  화면이 한 프레임 스친다). 가사와 동시에 켜면 가사가 위, 자막이 아래에 놓인다.
  **번역은 우리가 문장을 번역하지 않고 YouTube의 번역 트랙을 받는다**(캡션 URL에
  `tlang=<코드>`). 자막 한 편을 `deep-translator`로 돌리면 수백 번 왕복이 생기고 문맥이
  끊겨 품질도 떨어진다 — 가사 번역(짧은 한 덩어리)과는 사정이 다르다. 번역본을 못 받으면
  **원본으로 한 번 더 시도**한다(번역이 없다고 자막 자체를 잃을 이유는 없다).
  **자동 자막 목록에서 번역본을 걸러 내는 것이 필수**다: 실측 결과 한 영상의
  `automatic_captions`에 312개(번역 가능한 모든 언어)가 들어 있었고, 그대로 나열하면
  원래 언어가 무엇인지도 알 수 없다 — URL에 `tlang=`이 있으면 번역본으로 보고 제외한다.
  원본 자동 자막의 키는 `en-en`·`de-de` 꼴이라 `en`으로 정규화해야 수동 자막 `en`과
  중복되지 않는다(실측으로 발견). 트랙 목록(yt-dlp)·파일 내려받기(HTTP)는 모두 QThread에서
  하고 영상별로 캐시하며, 늦게 도착한 결과는 그 사이 다른 트랙·영상으로 넘어갔으면 버린다.
  지난번에 고른 언어는 설정에 남아 **다음 영상에도 같은 언어가 있으면 이어서 켠다**
  (영상마다 다시 고르게 하면 '늘 쓰는 설정'이 매번 사라진다). 회귀 테스트:
  `tests/unit/infrastructure/test_subtitle_parsers.py`(자동 자막의 단어 타이밍 태그·반복 줄),
  `tests/unit/infrastructure/test_youtube_subtitles.py`(번역본 제외·키 정규화·번역 폴백),
  `tests/gui/test_video_subtitles.py`(두 칸 동시·빈 구간·늦은 결과 폐기).
- **읽는 글(요약·가사) 글자 크기** — 요약과 가사는 읽으라고 있는 글인데 크기가 코드에
  박혀 있었다. `Ctrl` + `+`/`-`로 조절하고 `Ctrl+0` 또는 각 헤더의 **배율 버튼**(현재 %를
  표시하며 누르면 기본값)으로 되돌린다. 단일 키는 플레이어 몫이라 쓰지 않는다(입력 규칙).
  배율은 **두 영역이 공유**하고(글자 크기는 화면 설정이지 영역별 취향이 아니다) 전역
  설정(`detail_text_scale`)에 저장한다. 가사는 줄마다 스타일시트로 크기를 주므로 배율이
  바뀌면 다시 그리되 **현재 강조 줄은 유지**한다. 0.1 누적이 `1.97000…2`로 저장되지 않도록
  `clamp_scale`이 소수 둘째 자리에서 끊는다(자막 배율에서 겪은 문제).
- **재생 컨트롤 아이콘 크기** — 13px/24px(원래) → 26px/48px(2배, `gui/widgets/player/
  controls.py`) → **28px/38px**(상자를 20%가량 줄이되(48→38) 글자 대 상자 비율은 오히려
  키움(26/48=54% → 28/38=74%), 안쪽 여백도 `2px 6px` → `0px 1px`로 최소화)로 두 단계
  조정했다. 상자만 줄이고 글자 비율·여백을 그대로 두면 작아진 상자 안에 여백만 커 보여
  '꽉 찬' 느낌이 나지 않는다 — 그래서 상자를 줄이는 변경은 항상 비율 확대·여백 축소를
  함께 한다. **바 높이는 `_ICON_BOX + 48`**(여백+슬라이더 행 몫은 아이콘 상자 크기와
  무관하게 항상 48px)로 유도해, 상자 크기를 바꿀 때마다 높이 상수를 손으로 다시
  계산하지 않는다.
- **이어보기(재생 위치)** — `videos.last_position_ms`·`last_played_at`. **기기마다 보던
  지점이 다르므로 동기화 캡처 대상이 아니다**(view_count와 같은 취급). 판정은 도메인
  규칙(`VideoAggregate.update_playback_position`): 15초 미만은 기록하지 않고(잠깐 눌렀다 만 것),
  97% 이상이면 위치를 지우고 `watched`를 세운다(끝 직전으로 되돌아가면 오히려 불편하다).
  저장은 재생 중 5초마다 + 화면을 떠날 때 한 번 더이며, 아그리게이트 전체 저장 대신
  **가벼운 UPDATE 전용 경로**(`save_playback_position`)를 쓴다(반복 호출되므로).
  상세를 열면 저장된 지점으로 seek 하되 **자동 재생하지 않는다** — 목록에서 눌렀을 뿐인데
  소리가 나면 놀란다(재생목록 자동 전환만 `autoplay`). 카드 썸네일 바닥의 진행률 띠는
  `_paint_progress_bar`가 그리고, 정렬 '최근 재생순'·검색 `in_progress_only`가 짝을 이룬다.
  회귀 테스트: `tests/integration/test_resume_playback.py`, `tests/gui/test_resume_ui.py`.
- **스트리밍 재생 실패 → 브라우저 튕김 (해결)** — "카테고리·추천 영상을 재생하면 앱에서
  안 나오고 브라우저가 열린다"는 신고의 원인은 **두 가지**였다.
  ① **간헐적 403**: 기본(web) 클라이언트로 받은 googlevideo URL이 같은 영상인데도
  어떤 때는 200, 어떤 때는 403을 돌려준다(실측으로 재현 — PO token/SABR 전환기의
  서버측 거부로 보인다). 같은 순간 `android` 클라이언트로 받으면 정상이었다.
  ② **첫 실패에 곧바로 포기**: `_on_play_failed`가 원인과 무관하게
  `QDesktopServices.openUrl`로 브라우저를 열었고 **로그를 전혀 남기지 않아**,
  사용자 로그를 받아도 실패 흔적이 없었다.
  대응: `_StreamWorker._run_stream`이 `_STREAM_CLIENTS`(기본→android→ios→tv)를 돌며
  URL을 받고, **넘기기 전에 `_stream_playable`로 검증**해 거부되면 다음 클라이언트로 간다.
  **검증 요청은 실제 재생 주체(Qt Multimedia의 FFmpeg 백엔드)와 똑같아야 한다** — 이걸
  틀려서 한 번 헛돌았다: 처음엔 `Range: bytes=0-1`(제한 범위)로 확인했는데, 같은 URL이
  제한 범위에는 206을 주고 **ffmpeg가 파일을 열 때 보내는 `Range: bytes=0-`(열린 범위)
  에는 403**을 주는 경우가 있어 검증만 통과하고 재생은 실패했다. 그래서 `_PROBE_RANGE`는
  열린 범위이고 UA도 ffmpeg 기본값(`Lavf/...`)을 쓴다(yt-dlp 전용 헤더로 검증하면 같은
  이유로 위양성이 난다). 응답 본문은 읽지 않고 즉시 닫는다. 클라이언트
  교체 재시도는 `_is_youtube`일 때만 한다(다른 사이트엔 의미 없는 왕복).
  **검증이 전부 실패해도 URL을 하나라도 얻었으면 그대로 재생을 시도**한다 — 확인 요청이
  막히는 환경(프록시)에서 재생을 통째로 잃지 않기 위한 안전판이며, 최소한 예전 동작과
  같다. 고화질 병합 경로도 같은 클라이언트 목록을 돌고, 전부 실패하면 **낮은 화질
  스트리밍으로 폴백**한다(브라우저로 튕기는 것보다 낫다). 재생 중 QMediaPlayer 오류는
  `_MAX_STREAM_RETRIES`(1)회까지 새 URL로 조용히 재시도하되 **로컬 파일 재생 오류는
  재시도하지 않고**(같은 파일이라 무의미), 예산은 실제 재생이 시작될 때
  (`_on_playback_state`의 PlayingState) 회복한다 — 스트림을 받을 때마다 초기화하면
  오류→재시도가 무한 반복된다. `_pick_stream_url`은 **muxed(영상+오디오) 포맷만**
  고른다(예전 마지막 폴백은 `url`만 있으면 무엇이든 집어 영상 전용 포맷으로 무음·실패를
  만들었다). 실패 시 브라우저를 열지 않고 `InlinePlayer.show_playback_error`로 이유를
  영상 자리에 띄우며, 브라우저로 갈지는 상단 `🌐` 버튼으로 사용자가 고른다.
  회귀 테스트: `tests/gui/test_stream_fallback.py`.

## 전사 모델을 "받아 뒀는지" 묻는 두 가지 방법 (v1.27.1)

`faster-whisper`에는 "이 모델이 받아졌나"만 묻는 API가 없다. 판정하는 유일한 공식
경로가 `WhisperModel(..., local_files_only=True)` 생성인데, 이것은 **성공하면 모델을
메모리에 올린다**. 전사를 시작하기 직전이라면 오히려 이득이지만(곧 쓸 것을 미리
올린다), 설정 화면처럼 **목록만 보여주는 자리**에서는 화면을 여는 것만으로 수백 MB가
붙잡힌다 — 목표 사양이 4GB RAM 인 앱에서 그냥 넘길 값이 아니다.

그래서 경로를 둘로 나눴다:

| 용도 | 함수 | 대가 |
| --- | --- | --- |
| 전사 직전 판정 | `WhisperTranscriber.is_model_ready()` | 모델을 올린다(곧 쓰므로 이득) |
| 목록·용량·삭제 | `is_model_downloaded()` · `model_disk_bytes()` (모듈 함수) | 파일만 본다 |

파일 기반 판정은 HuggingFace 캐시 규약(`models--Systran--faster-whisper-<key>`)에서
**크기가 0이 아닌 `model.bin`**을 찾는다. 내려받다 끊기면 폴더는 생기고 가중치는
`.incomplete` 로 남으므로 이 조건이 완성본을 가른다.

**틀려도 복구된다**는 것이 이 판정을 싸게 유지하는 근거다. 있다고 잘못 보면 "내려받는
중" 안내만 안 뜨고(실제 내려받기는 `transcribe()`가 `local_files_only=False`로 한다),
없다고 잘못 보면 `download_model()`이 완성본 앞에서 즉시 끝난다. 그래서 여기서는
정확도보다 **가벼움**을 택했다.

회귀 테스트: `tests/unit/infrastructure/test_whisper_model_files.py` —
특히 `TestNoModelLoad`가 `_load`를 실패로 바꿔 놓고 목록·용량을 읽어, **모델을 올리면
테스트가 깨지게** 고정한다.

## 음성 인식 중단 — 단계를 구분해야 버튼이 거짓말을 하지 않는다 (v1.27.1)

협조적 중단은 `should_stop()`을 **세그먼트 경계에서** 확인한다. 그래서 전사가 도는
동안에는 한 박자 안에 멈추지만, **모델을 내려받는 동안에는 전혀 걸리지 않는다** —
내려받기가 끝나야 첫 판정이 돌기 때문이다. 이 단계에서 중단 버튼을 띄우면 눌러도
몇 분간 아무 반응이 없어 고장처럼 보인다.

그래서 `SubtitleTab.show_transcribing(text, *, stoppable=...)`으로 **지금 멈출 수 있는
단계인가**를 화면이 받는다. 상세화면(`mixins/player.py`)이 `_asr_downloading` ·
`_asr_stopping` 두 플래그로 단계를 기억하며 세 가지를 지킨다:

1. 내려받는 중에는 버튼을 숨기고, 그래도 중단을 부르면(외부 경로)
   "모델 내려받기가 끝나면 멈춥니다"라고 사정을 말한다.
2. **중단 뒤 뒤늦게 도착한 진행률이 중단 안내를 덮지 않는다.** 덮으면 눌린 줄 모른다.
3. **중단해서 0줄인 것과 끝까지 듣고 말을 못 찾은 것을 구분한다.** 중단한 사람에게
   "소리에서 말을 찾지 못했습니다"라고 하면 기능이 고장 난 것처럼 들린다.

회귀 테스트: `tests/gui/test_transcribe_stop.py`.

## 자막 번역은 묶어 보내되, 정렬이 깨지면 되돌린다 (v1.29)

번역기(`ITranslator`)는 **한 줄씩** 호출하는 설계다 — 가사 40줄에 맞춰 만들었고,
줄마다 독립적으로 try/except해 한 줄의 실패가 나머지에 번지지 않게 돼 있다. 자막은
수백~수천 줄이라 그대로 쓰면 왕복이 그만큼 나고, 몇 분이 걸리며 백엔드가 막기도 한다.

그래서 40줄씩 줄바꿈으로 이어 한 번에 보낸다(500줄이면 13번 왕복). **대신 정렬이
깨질 위험이 생긴다** — 번역기가 줄을 합치거나 나누면 원문과 번역의 짝이 어긋나고,
그러면 엉뚱한 시점에 엉뚱한 말이 뜬다. **틀렸다는 티조차 나지 않는 실패**라 가장
고약하다.

안전장치는 단순하다: 묶음마다 **돌아온 줄 수를 센다**. 맞지 않으면 `split_chunk`가
`None`을 돌려주고, 그 묶음만 한 줄씩 다시 한다. 억지로 맞추지 않는다.

곁가지 규칙 둘:

* **실패한 자리는 원문을 남긴다.** 빈 줄로 두면 그 시점에 자막이 사라져, 번역 실패인지
  원래 말이 없는 것인지 알 수 없다.
* **결과가 원문과 똑같으면 저장하지 않는다.** 번역기가 통째로 실패한 경우인데, 그걸
  '번역본'이라고 저장하면 목록만 늘고 쓸모는 없다.

원본을 덮지 않고 `tr-ko`라는 별도 언어 키로 저장하는 것은 음성 인식(`asr-auto`)과
같은 판단이다 — 원문으로 검색하고 싶을 수도, 번역이 엉망일 수도 있다.

## 앱 내 재생이 항상 360p였던 진짜 이유 (v1.32)

### 증상

"앱 내 플레이어를 재생하면 늘 해상도가 매우 낮은 것으로 한정적으로 재생된다."

### 원인 — 포맷 선택 버그가 아니라 구조다

기본 화질은 `best[ext=mp4]/best` 였다. yt-dlp에서 `best`는 "가장 좋은 **muxed**
포맷"이고, YouTube가 내주는 muxed는 **itag 18(360p) 하나뿐**이다.

```
[default] total=33 muxed=1
   MUX 18 mp4 360 https avc1 mp4a      ← 영상+소리가 함께 든 포맷은 이것 하나
   video-only heights: [144, 240, 360, 480, 720, 1080, 1440, 2160]
```

즉 원본이 4K여도 이 선택자는 **항상** 360p를 골랐다. "자동 (빠른 재생)"이라는
라벨이 지키지 못할 약속을 하고 있었던 셈이다. `ios`·`tv` 클라이언트로 HLS를
받는 우회로도 확인했으나 지금은 전부 추출 자체가 실패한다.

### 그러면 왜 고화질 URL을 그냥 재생기에 넘기지 않았나

넘길 수 없었다. 같은 1080p URL에 요청 형태만 바꿔 보면:

| 요청 | 응답 |
| --- | --- |
| `Range: bytes=0-` (열린 범위) | **403** |
| `Range: bytes=0-1000` (경계 있는 범위) | 206 |
| `?range=0-1000` (쿼리 파라미터) | 200 |

**ffmpeg는 파일을 열 때 정확히 `Range: bytes=0-`를 보낸다.** 그래서 Qt(FFmpeg
백엔드)에 고화질 URL을 주면 언제나 403이다. `constants.py`의 `_PROBE_RANGE`
주석이 적어 둔 "열린 범위 403"과 같은 현상인데, 고화질에서는 간헐적이 아니라
**항상** 그렇다. 앱이 "전체를 받아 두고 재생"(`_run_merge`)으로 갈 수밖에
없었던 이유가 이것이다.

제약이 하나 더 있다. **요청당 허용 바이트 상한이 포맷마다 다르다** — 1080p(137)는
2MB 요청에 206을 주지만 오디오(140)는 2MB에 403, 128KB에 206을 준다. 비트레이트에
비례하는 상한으로 보인다.

### 해결 — 로컬 중계 + 실시간 remux

`infrastructure/streaming/relay.py`가 127.0.0.1에 중계 서버를 띄운다. 재생기의
**열린 범위** 요청을 받아, 상위로는 **경계 있는 작은 조각**으로 되묻어 이어
붙인다. 재생기 입장에서는 평범한 로컬 파일이다. `/play.mp4`는 ffmpeg를 띄워
영상+오디오를 `-c copy`로 합쳐 fragmented mp4로 흘린다.

실측: 1080p 첫 바이트까지 **0.97초**, 3MB까지 1.58초. 전체(245MB)를 받지 않는다.

### 밟은 함정 셋

1. **조각을 줄여도 크기가 안 줄었다.** `stop = min(pos + chunk - 1, end)` 라
   남은 길이가 조각보다 짧으면 `chunk`를 반으로 줄여도 실제 요청 크기는 그대로다.
   403 → 축소 → 같은 요청 → 403 의 무한 루프가 됐다.
2. **포기할 때 클라이언트를 매달아 뒀다.** `Content-Length`를 이미 약속한 뒤
   조용히 돌아가면 재생기는 남은 바이트를 **영원히 기다린다**(실측: 요청이
   타임아웃까지 멈춤). 연결을 끊어 "끊겼다"를 즉시 알려야 상위가 재시도한다.
3. **일시적 거부를 크기 문제로 오해했다.** 통하던 크기가 403을 받으면 그것은
   속도 제한이지 상한 문제가 아니다. 줄이면 요청이 더 잦아져 악화된다 — 실측으로
   seek 첫 바이트가 1초대에서 22초로 나빠졌다. 그래서 `StreamSource.proven`으로
   "한 번이라도 통한 크기인가"를 구분해, 통하던 크기면 **쉬었다 같은 크기로**
   재시도한다.

### 남은 제약 — 먼 오프셋은 원본이 거부한다

seek 구현 자체는 정확하다(ffmpeg가 `bytes=43655361-`로 올바르게 Range-seek 한다).
그런데 원본이 그 요청을 거부한다:

```
앞 0%     start=        0   헤더Range=206   쿼리range=200
중간 54%  start= 43692479   헤더Range=403   쿼리range=403
뒤 90%    start= 72820799   헤더Range=403   쿼리range=403
```

요청 형태의 문제가 아니라 **먼 오프셋 접근 자체를 막는다**(PO token 없는 URL은
순차 재생만 허용하는 것으로 보인다). 이것은 스트리밍만의 문제가 아니다 — 같은
이유로 **기존의 전체 다운로드도 중간에서 403으로 멈춘다**(실측: yt-dlp 자체
다운로드가 9%에서 403).

그래서 재생이 같은 자리에서 되풀이해 끊기면 `_fall_back_to_merge`가 예전 방식으로
내려간다. 처음부터 순차로 받는 것은 허용되므로, 기다림을 치르고 seek까지 되돌려
받는 쪽을 택한 것이다. 이 판정은 **영상마다 새로 한다**(`_reset_stream_mode`).

### seek을 우리가 맡는다

파이프로 흘리는 fragmented mp4는 길이도 없고 되감기도 안 된다. 그래서:

- 길이는 yt-dlp 값(`_stream_duration_ms`)으로 대신 답한다(`_effective_duration`).
  이걸 빼먹으면 진행 막대가 채워진 채 멎는다.
- seek은 `?ss=` 로 **새 연결을 연다**. 재생기 위치는 매번 0부터 다시 세므로
  영상 기준 위치 = 재생기 위치 + `_stream_offset_ms` 다.
- 모든 seek 진입점을 `_seek_to` 하나로 모으고 300ms 타이머로 합친다 — J/L 연타마다
  ffmpeg를 새로 띄우면 화면이 멎는다.
- 상위가 조각을 거부하면 **중간에서도 EndOfMedia**가 온다. 그대로 믿으면 재생목록이
  멋대로 다음 곡으로 넘어간다 → 끝 근처일 때만 '다 봤다'로 친다.

### 먼 seek 뒤 '소리만 나오고 영상이 안 나오는' 반쪽 스트림

seek으로 먼 지점을 열면 원본이 영상·오디오 Range를 **따로** 403으로 거부한다(실측:
ss=20에서 영상 22MB·오디오 1MB 지점). 예전에는 `_pump_source`가 거부된 원본 **하나만**
포기했고, ffmpeg는 나머지 입력으로 계속 돌았다. 그래서 영상 또는 소리 한쪽만 나오는
스트림이 되었고 — 재생기는 EndOfMedia도 오류도 받지 못해 복구 경로(재시도 → 병합
폴백)가 **발동하지 않았다**(실측: 오디오가 3.3초에서 멈춘 채 영상 프레임만 계속 흘렀다).

- 중계는 원본이 **영구 거부**(백오프·URL 갱신 소진)되면 그 세션의 remux ffmpeg를 죽인다
  (`RelaySession.abort_remux`). 재생기는 즉시 `ResourceError`를 받는다.
- 죽이기 전에 `is_peer_connected`로 **ffmpeg가 아직 이 연결에 붙어 있는지** 본다 —
  seek으로 끊긴 옛 연결의 펌프가 뒤늦게 포기하며 새 seek의 멀쩡한 ffmpeg를 죽이면 안 된다.
- 플레이어는 `_stream_offset_ms > 0`인 remux 오류(= 먼 오프셋 거부)면 재시도 없이
  현재 위치로 곧장 병합 폴백한다. 재시도는 `?ss=0`부터라 위치가 사라지고 같은 실패를 되풀이한다.
- 교훈: **입력이 둘인 파이프는 한쪽이 죽어도 출력이 끝나지 않는다.** 부분 실패를 전체 실패로 올려야 상위 복구가 돈다.

### 먼 seek이 막히던 진짜 원인 — yt-dlp가 JS 챌린지를 못 풀었다 (2026-10)

처음에는 "원본 제약이라 우회 불가"로 판단하고 360p 강등 안내 토스트만 붙였다 — **틀린
결론이었다.** 사용자가 "전혀 개선되지 않았다"고 다시 알려 와 경계를 정밀하게 쟀다:

- 대체 클라이언트(android_vr 등) URL은 **오프셋과 무관한 고정 경계**가 있었다 — 1080p(77MB)
  에서 21MB까지 206, 22MB부터 403(≈ 처음 60초 분량). 1MB씩 순차로 걸어가도 같은 자리에서
  막혔다. "먼 오프셋 거부"가 아니라 **PO token/챌린지 없는 URL의 1분 상한**이다. 즉 seek뿐
  아니라 처음부터 틀어도 1분 뒤에 끊긴다.
- 대체 클라이언트로 밀린 이유: yt-dlp의 `js_runtimes` 기본값은 `{"deno": {}}` 뿐인데
  이 PC에는 node만 있어 `JS runtimes: none` — 기본(web) 클라이언트가 n/서명 챌린지를 못 풀어
  쓸 수 없었다. yt-dlp 자체도 90일 넘게 낡아 있었다.
- 최신 yt-dlp(`yt-dlp[default]` → `yt-dlp-ejs` 포함) + `js_runtimes={"node": {}}`로 기본
  클라이언트를 쓰면 **영상·오디오 모두 0~99% 어느 오프셋이든 206**이다.

해결: `utils/ytdlp_runtime.js_runtime_opts()`가 설치된(또는 `bin/`에 번들된) 런타임을
찾아 **모든 `YoutubeDL` 호출에** 켠다(계약 시험이 빠뜨린 호출부를 잡는다). 런타임이 하나도
없으면 경고를 남기고 예전처럼 대체 클라이언트로 내려간다 — 그때만 360p 강등 토스트
(`quality_notice.should_notify_downgrade`)가 의미가 있다.

교훈: **"외부 제약이라 못 고친다"는 결론은 경계를 정확히 잰 뒤에 내린다.** 의존 도구의
진단 출력(`yt-dlp -v`의 `JS runtimes`·`PO Token Providers`)을 먼저 봤다면 한 번에 찾았다.

#### 같이 찾은 두 번째 원인 — seek마다 남은 응답을 통째로 읽었다 (20초+)

JS 런타임을 켜자 먼 오프셋도 열렸지만 seek 한 번에 21~26초가 걸렸다(사용자가 말한
"처음 한 번은 느리다"의 정체). ffmpeg 8.1 로그에 시각을 찍어 보니
`Soft-seeking to offset 37798998 by draining 80649855 remaining byte(s)` 한 줄이 20초였다.
중계의 `/v`·`/a` 응답이 HTTP/1.1 keep-alive라, ffmpeg가 `-ss` seek 때 **새 Range 요청을
여는 대신 연결을 재사용하려고 현재 응답의 나머지(77MB)를 다 읽어 비웠고**, 그 연결은
이미 닫혀 있어 `Error reading HTTP response: End of file` 뒤 재연결까지 했다.
`_serve_source` 응답에 `Connection: close`를 주자 같은 seek이 **2.1초**가 됐다
(통계: 2 connections, 2 requests, 0 retries).

## 재생 성능(배치 6) — 중복 추출 제거·영상 info 캐시·seek 쿨다운 (2026-10)

### 실측한 중복
- 상세 진입 + ▶ 동안 yt-dlp 추출이 **둘 동시에** 돈다(자막 목록·스트림, 각 3~4초). 화질
  전환은 +1회, ⬇ 화질 메뉴는 +1회였다. 고화질 ▶ → 첫 프레임 3,057ms.
- 추출 1회의 실체는 HTTP 4건 + JS 챌린지(deno/node) 프로세스다. 서명·n 파라미터는 추출
  단계에서 URL에 이미 풀려 들어가므로, **화질만 다시 고르는 일은 네트워크가 필요 없다**
  (원본에 `process_ie_result`: 약 0.1초, HTTP 0, 하위 프로세스 0, 선택 결과가 새 추출과 3/3 일치).

### 캐시 설계 — 처리 전 원본을 들고, 화질은 처리 시점에 고른다
- `VideoInfoCache`(`infrastructure/media/video_info_cache.py`)는 `extract_info(process=False)`
  원본을 `(url, client)`로 캐시한다. 워커는 `copy.deepcopy(raw)`를 새 `YoutubeDL({"format": …})`
  의 `process_ie_result`로 처리한다. 방법 (c)를 골랐다 — 공개 API만 쓰고 새 추출과 같은 처리
  경로(`http_headers`·정렬·포맷 ID)를 타서 `_to_sources`·`_pick_stream_url`을 고치지 않는다.
  처리는 입력을 고치므로 **원본은 절대 그대로 넘기지 않는다**(시험이 오염을 고정한다).
- **자막 목록도 같은 원본에서 뽑는다**(`IVideoSubtitleSource.tracks_from_info`). 함정: yt-dlp
  확장기는 `writesubtitles`/`writeautomaticsub`이 꺼져 있으면 `subtitles`·`automatic_captions`를
  **채우지 않는다**. 그래서 원본 추출 옵션에 둘을 켠다(`skip_download`라 내려받지 않는다).
  쿠키가 있는 사용자는 로그인 상태 자막이 보일 수 있어 기존 경로를 그대로 쓴다.
- TTL = `min(googlevideo expire − 300초, 1800초)`. 실측 expire 여유가 6시간이라 사실상
  30분이다. 남은 시간이 300초 이하면 캐시하지 않고, `expire`가 없거나 파싱되지 않으면 30분이다.
  적중해도 TTL을 늘리지 않는다. 항목은 최대 6개(원본 JSON 영상당 ~600KB), LRU로 버린다.
- **진행 중 요청을 합친다.** load와 ▶가 150ms 간격으로 같은 키를 묻는다 — 두 번째는 기다렸다
  결과(또는 같은 예외)를 받는다. 끝난 요청은 바로 지우고 실패는 캐시하지 않는다.

### 반드시 캐시를 우회하는 경로(`fresh=True`)
캐시가 만료·거부된 URL을 되풀이해 주면 재생이 영영 안 살아나므로 다음은 항상 우회하고
새 결과로 캐시를 갈아 끼운다(진행 중 요청에도 합류하지 않는다).
- 중계 `refresh`(재생 중 URL 만료) — 원래 클라이언트로 `(url, client, True)`.
- 대체 클라이언트 순회 — 실패(추출 오류·포맷 없음·검증 403) 뒤의 모든 조회는 fresh.
  403을 낸 키는 `invalidate`로 캐시에서도 버린다(다음 ▶가 같은 URL을 받지 않게).
- `_on_error` 재시도 — 방금 실패한 URL이 캐시에 남아 있으므로 **다음 워커 한 번만** fresh.
- 병합(`_run_merge`, `download=True`)은 다운로드를 겸하는 추출이라 캐시 대상이 아니다.

### seek 쿨다운(A8)
- 단발 seek이 300ms 디바운스를 기다릴 이유는 없다. 직전 커밋 뒤 600ms(`SEEK_IMMEDIATE_GAP_MS`)
  가 지났으면 즉시 커밋하고, 그 안의 연타만 300ms 타이머로 합친다(J/L 5연타 = 커밋 2회).
  즉시 커밋의 메인 비용은 `stop()`+`setSource(?ss=)` 약 17ms(최대 37)다.
- 즉시·타이머 커밋 모두 `_last_seek_commit_ms`를 갱신하고, `_close_remux`가 None으로 되돌려
  새 스트림의 첫 seek은 즉시 나간다. 모든 seek은 `_seek_to` 하나를 거치고 대기 중 `position_ms`
  는 목표를 답한다. **자동 재연결**(끊긴 remux를 같은 지점에서 다시 여는 `_on_media_status`)은
  `_seek_to(pos, debounce=True)`로 쿨다운과 무관하게 모은다 — 즉시 되풀이되면 상위를 두드린다.
- 비 remux 소스는 그대로 재생기에게 맡긴다.

### D1 조사 결론 — 재생 중 0.2~0.5초 정지는 이 PC의 환경 현상이다
- 정지는 길이로 뚜렷이 두 무리다. 환경형 467~578ms(파이썬 호출·Qt 로그 없음)와 앱형 50~82ms.
- 앱 코드가 없는 순수 PyQt6(창 없음), Qt 없는 ctypes Win32 `PeekMessage` 루프에서도 재현된다
  (`PeekMessage` 한 번이 140~480ms). 앱·Qt Multimedia 원인은 반박됐다. 전역 훅·창 감시 상주
  프로그램(PowerToys 등)이 유력하나 특정하지 않았다.
- 따라서 **'최대 메인 정지'를 수용 기준으로 쓰면 이 PC에서는 어떤 개선도 500ms 아래로 못
  간다** — 환경형(≥350ms, 파이썬 호출 없음)을 제외하거나 앱 호출의 메인 소요로 잰다.
  앱이 만드는 정지는 프레임 2~5개 수준이라 D1 개선 항목은 만들지 않았다. 원자료는
